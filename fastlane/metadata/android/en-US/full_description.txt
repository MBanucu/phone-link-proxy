Phone link proxy is the SOCKS5 listener a laptop's tunnel talks to when an
Android phone is the uplink. It is small on purpose: no AndroidX, no Gradle and
no third-party libraries, so the build is aapt2, javac, d8 and apksigner and
needs nothing from the network once the SDK is in the store.

Why it exists:

- Egress is cellular by construction. On a laptop-hosted access point the
  phone's default network is the laptop, so a socket opened on the default
  route comes back to the host that asked for it. The app holds an active
  cellular network request and resolves and connects on it.
- It binds all interfaces, so the port is the same on a Wi-Fi, hotspot or USB
  link and survives the address changing. Binding is not a transport choice:
  by default the SSID gate still keeps the port closed on any network but the
  one you name.
- By default the port only opens while the phone is a client of the SSID the
  proxy names, so the phone can sit on a hotel or cafe network without offering
  a relay to it. `any_network` removes that gate; it is not a separate transport
  mode, and it does not by itself make USB fallback work.
- The listener requires the username and password you configure. It runs
  without authentication only when you tick "Listen without authentication"
  (or pass `anonymous=true`), and then anyone who can reach the port can relay
  through the phone.
- The wake lock is held only while a client is connected.
- No screen automation: the service is exported and guarded by
  android.permission.DUMP, which adb holds and ordinary apps do not, so a
  wired or wireless adb session starts and stops the listener without the phone
  being unlocked.

Several proxies can be saved, each with its own port, credentials, SSID and
settings, and a Quick Settings tile starts and stops the ones it is told to.
Every proxy keeps its own log and traffic counters. The whole set can be
exported to a file and imported again, which is the answer to losing them to a
signing-key change or a reset phone.

The app documents its own adb contract in About this app, which is also what
the service prints for dumpsys. Credentials stay in the app's private,
non-backed-up preferences; they are device-protected so the listener can start
before the first unlock, which means the app can read them while the device is
locked. The state file adb can read holds no credentials, and an export you
write yourself is plain text and says so.
